# 双语内容生成方案（免费优先）

> 需求 3 的完整答复。结论先行：**默认走免费的本地大模型，商用 API 只作为兜底**。
> 本地模型不仅零成本，还天然满足《需求.md》第 8 条的合规要求——标题和摘要一个字节都不离开这台机器。

---

## 1. 先明确约束

| 约束 | 来源 | 对方案的影响 |
|---|---|---|
| 只存标题、摘要、导语，不抓正文 | 需求.md 第 1、7 条 | 翻译对象只有 3 个短字段，单个模型完全够用，不需要长文本能力 |
| 绝不对外分享、上传 | 需求.md 第 8 条 | **上传给云端 API 本身就是一种外发**，这是"本地优先"最硬的理由 |
| 温和、低频 | 需求.md 第 4 条 | 翻译必须异步、批量、有并发上限，不能阻塞采集 |
| 数据会无限增长 | 用户本次需求 4 | 必须去重缓存 + 每日上限，否则成本会随时间线性上升 |

---

## 2. 四条可选路线

| 路线 | 成本 | 数据是否出本机 | 质量 | 结论 |
|---|---|---|---|---|
| **A. 本地大模型**（Ollama / LM Studio / llama.cpp / LocalAI） | **0 元** | **不出** | 好（7B 级别足以处理新闻标题） | ✅ **默认方案** |
| B. 自建翻译引擎（LibreTranslate / Argos） | 0 元 | 不出 | 一般，专有名词差 | 备选，模型更小更省内存 |
| C. 免费额度的云翻译（MyMemory、各类免费 API） | 0 元 | 出本机 | 参差，有速率限制 | 不建议（与第 8 条冲突） |
| **D. 商用大模型 API**（DeepSeek / 通义 / Kimi / OpenAI） | 按量付费 | 出本机 | 最好、最快 | ⚠️ **仅在本地不可用时兜底** |

**路线 D 之外的零成本补充手段**（不需要任何模型）：

- **跨源同事件对齐**：同一条通稿常被中英文源各发一次。指纹/标题相似度配对后，中文源提供中文、英文源提供英文，双方互为译文，一次翻译都不用做。缺点是覆盖面有限，且配对错误会产生错误对应，所以本版本**未启用**，仅列为后续可选。
- **分类名与界面词典**：45 个分类的中英文名已经直接存在 `categories.name_en`，界面文案走 i18n 词典。这部分是纯静态数据，零成本，本版本已实现。

## 3. 本仓库的实现架构

```
采集入库 ──► 原文侧填充（免费的纯规则判定，无需模型）
              │  Article.Title/Summary/Lead 永远是原文，不被译文覆盖
              ▼
        trans_status = pending
              │
              ▼
   后台 worker（每 N 秒一批，可配置）
              │  ① 探活：接口不通就整批跳过，不消耗重试次数
              │  ② 成本护栏：当日已达上限就停
              │  ③ 取一批待翻译文章
              ▼
      逐篇：算 sha256(文本) ──命中缓存？──► 直接用，0 成本
              │ 未命中
              ▼
      一次请求批量翻译（标题 + 摘要，按 translate_scope 决定范围）
              │
              ├─ 成功 → 写入译文 + 缓存 + trans_status=done
              └─ 失败 → trans_attempts+1，3 次后不再重试（可在设置页一键重置）
```

### 3.1 数据字段（`articles` 表）

| 字段 | 含义 |
|---|---|
| `title` / `summary` / `lead` | **原文**，采集时写入，任何情况下都不被译文覆盖 |
| `lang` | 原文语言（`zh` / `en`），由 `internal/langdetect` 纯规则判定 |
| `title_zh` / `title_en` / `summary_zh` / `summary_en` / `lead_zh` / `lead_en` | 双语内容。原文那一侧在入库时就填好 |
| `trans_status` | `pending` / `done` / `failed` / `skipped` |
| `trans_attempts` | 已尝试次数，上限 3 |
| `trans_error` | 最近一次失败原因，直接显示给用户 |

`translations` 表是**翻译缓存**，主键为 `(sha256(原文), 目标语言)`。同一条通稿被两个源抓到、或应用重启后，都不会再次调用模型——这是成本不随时间增长的关键。

### 3.2 语言判定（`internal/langdetect`）

不引入 CLD3 / fastText 这类需要模型文件的依赖，用 CJK 码点占比判断：

- 汉字占"字母类字符"比例 ≥ 20% → 中文
- 出现假名或谚文 → 直接判为未知（日韩共用汉字，纯比例会误判成中文）
- 其余 → 英文

纯规则、无依赖、可测试，对新闻标题足够。判定结果决定"哪一侧是原文"，从而决定要翻译的方向。

### 3.3 Provider 抽象（`internal/service/translator/provider.go`）

```go
type Provider interface {
    Name() string
    Model() string
    Translate(ctx context.Context, texts []string, targetLang string) ([]string, error)
}
```

只有一个实现 `OpenAICompatProvider`，走 `POST {base}/chat/completions`。**一个实现覆盖所有现实选项**：

| 服务 | Base URL | 说明 |
|---|---|---|
| Ollama | `http://127.0.0.1:11434/v1` | 免费，默认 |
| LM Studio | `http://127.0.0.1:1234/v1` | 免费，图形界面友好 |
| llama.cpp server | `http://127.0.0.1:8080/v1` | 免费，最省资源 |
| LocalAI | `http://127.0.0.1:8081/v1` | 免费 |
| DeepSeek | `https://api.deepseek.com/v1` | 付费，最便宜的中文质量 |
| 通义千问 | `https://dashscope.aliyuncs.com/compatible-mode/v1` | 付费 |
| OpenAI | `https://api.openai.com/v1` | 付费 |

设置页的"检测本地模型"会依次探测上表 4 个本地端口，把发现的模型列出来，点一下就把地址和模型名填好——用户不需要知道端口和模型名。

### 3.4 成本与稳定性护栏

| 机制 | 作用 |
|---|---|
| 接口探活（30 秒缓存） | 用户还没启动 Ollama 时，整批跳过且**不消耗重试次数**，启动后自动恢复 |
| 每日上限 `translate_daily_limit` | 付费 API 的硬刹车，默认 300 篇/天 |
| 翻译范围 `translate_scope` | 默认"标题+摘要"；本地模型慢时可只翻标题 |
| 重试上限 | 同一篇最多 3 次，避免坏数据空转 |
| 结果缓存 | 相同文本永不重复付费 |
| 批量请求 | 10 篇标题一次请求，而不是 10 次往返 |

### 3.5 界面表现

- 每张卡片有 `中文 / English` 两个 tab，切换显示对应语言的标题、导语、摘要。
- 徽章标明当前看的是**原文**还是**译文**，不会把译文伪装成原文。
- 该语言译文还没生成时，卡片显示原文并提示"该语言的译文尚未生成"，同时给出"立即翻译"按钮（单篇按需翻译，不排队）。
- 翻译服务未启用时，提示直接指向"设置 → 双语翻译"，而不是给一个按钮点了报错。

## 4. 落地步骤（推荐：全免费的本地模型）

```powershell
# 1. 安装 Ollama（一次性，官网下载 Windows 安装包）
#    https://ollama.com/download

# 2. 拉一个中英双向都不错的模型（约 4.7GB，一次性）
ollama pull qwen2.5:7b

# 3. 确认服务已起来
curl http://127.0.0.1:11434/v1/models
```

然后在应用里：**设置 → 双语翻译 → 打开开关 → 点"检测本地模型" → 点这一行的保存**。
地址和模型名会自动填好。再点"测试连接"，看到 `央行将利率维持在 4.5% 不变 -> Central bank keeps the rate at 4.5%` 就说明通了。

机器配置较低时的替代模型：

| 内存 | 建议模型 | 说明 |
|---|---|---|
| 16GB+ | `qwen2.5:7b` | 质量与速度平衡最好 |
| 8GB | `qwen2.5:3b` | 更快，专有名词略差 |
| 8GB 以下 | `qwen2.5:1.5b`，并把范围设为"仅标题" | 可用，但需要人工扫一眼 |

## 5. 质量与成本的实测建议

- **先只翻标题**：标题是列表页唯一能看到的内容，先用 `translate_scope=title` 跑一天，确认质量可接受再放到"标题+摘要"。
- **看缓存命中**：设置页有"缓存条目"计数。这个数字增长而"今日已翻译"不涨，说明去重在工作。
- **看失败原因**：`trans_error` 会原样显示提供方返回的错误（401 = Key 错，404 = 模型名错，connection refused = 服务没起来）。
- **不要一上来就开付费 API**：本地 7B 模型在新闻标题上的表现已经足够，付费的价值主要在速度和长摘要。

## 6. 后续可选增强（本版本未做）

1. **跨源同事件对齐**（零翻译成本）：用指纹或标题相似度把中英文源的同一事件配对，互为译文。需要额外的对齐阈值调参，配对错误会直接产生错误信息，风险高于收益，故未启用。
2. **术语表**：把常用机构名、人名固定译法注入 system prompt，提升一致性。
3. **自建 LibreTranslate**：内存占用比 7B 模型低得多，适合 8GB 以下机器，代价是专有名词质量下降。
4. **增量翻译**：目前一篇的标题和摘要要么都翻、要么都不翻；可以做成按字段独立翻译，摘要失败不影响标题可用。
